Modeling

Data scientistsSupervisorsIT leadership
In short

Most of the product's value comes from careful definitions, not exotic models: what counts as available, how long an outage really lasted, what usage really was. On top of those sit a handful of well-understood statistical methods, each chosen to answer one operational question, and one machine-learning model that has to prove itself before it is shown.

QuestionMethodWhy this method

Which printers fail most, fairly?Empirical-Bayes Gamma–Poisson rates with 90% credible intervals; report-card grades shrink toward the campus rateSmall samples don't top the list by chance
Did several printers fail together?Clusters of outages within 10 minutes across 3+ stations, tested against a Poisson rate for that hour and day typeTells a network or Wepa-side event from a busy moment

Does humid weather go with more jams?Mantel–Haenszel rate ratio, stratified by 6-hour block and weekday or weekendControls for the fact that humidity and printing both follow the clock
What if a desk stayed open later?Monte Carlo replay (1,000 runs) of real outages with extra desk coverage; fix times drawn from real desk-hour fixesAnswers staffing questions with the campus's own history
Where would one more printer help most?Greedy one-step p-median on walking times, weighted by busy-weighted downtimeDirectly minimizes students' extra walking

4.3 The outage-risk model

Each printer-hour becomes one example: time of day and week, whether a desk is open and how long until it opens, whether classes are in session, the kind of place, recent faults and warnings, recent usage, part levels. The label is whether an outage started in the next 24 hours.

4.5 The AI analyst

The Assistant is optional and runs only with an API key. It is an analyst with 16 read-only tools over the same data the pages use (station profiles, availability, incidents, repair times, supplies, usage, the report card, period comparisons, campus context, statistics, the risk model, investigations and the app's self-check).

  • Facts only. Every number it writes is checked against the tool results it received, allowing only honest unit restatements (minutes to hours, shares to percentages). Unsupported figures trigger one rewrite; anything still unsupported is flagged.
  • Read-only. It cannot change records, start updates or contact anyone.
  • Safe output. Answers are shown without links, images or HTML.
  • Scoped and fair. BSU printing only; never guesses who caused a problem; says "demo data" when it is.

Evaluation

IT leadershipData scientistsEngineers
In short

Each output is checked three ways: does the code do what the definition says (automated tests), is the evidence strong enough to show it (gates), and does the model actually beat the obvious alternative (held-out testing). Where the answer is no, the product says so instead of showing a confident number.

5.2 How the outage-risk model is scored

Walk-forward
Train on everything before a week, test on that week, for each of the last four weeks. The model never sees the future it is tested on.
Brier score
Mean squared error of the predicted probabilities; lower is better. Skill is the improvement over the baseline's Brier score.
AUC
How well the model ranks printers that did fail above those that didn't; 0.5 is a coin flip.
Calibration
Predicted chance versus observed rate in bins, shown as a chart, so "20%" means about 1 in 5.
Track record
Live predictions are logged and later compared with what happened.
For data scientistsThe baseline is deliberately strong: each printer's recent outage rate, shrunk toward the campus rate. An early version's baseline scored below 0.5 AUC because raw per-printer rates were noisy; shrinkage fixed it. A model that cannot beat this baseline is not shown.
For leadership"Not enough evidence yet" is a correct answer. The risk model stays hidden on new deployments until the data supports it; the page explains which condition is not met.

5.3 Software verification

  • 190 automated test cases run on every push and daily: the page parser against saved real pages, incident rules, the replacement rule, desk hours, the calendar, stories, Ask the data, routing (including an exact Held–Karp check), investigations, accounts and sign-in, security probes, the update pipeline, backup collectors, threat intelligence and durations.
  • Lint (ruff), static security analysis (bandit) and known-vulnerability scanning (pip-audit over the exact lock file) in continuous integration.
  • Attacker-style tests: every route without a session, path traversal, oversized uploads, cross-site posts, password guessing, forged or replayed backup messages, tampering with the audit trail.

5.4 Known limits

  • Usage is inferred from consumable levels; Wepa's job counts are not available.
  • Several alert codes are inferred from Wepa's legend until they appear on BSU's page.
  • Forecasting across semesters (ARIMA and similar) is deliberately postponed until a full academic year of live history exists.
  • Demo data is synthetic. On it, the models mostly rediscover patterns built into the simulator.
  • No multi-factor authentication yet; the administrator is a shared account.
